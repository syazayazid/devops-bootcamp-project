Connectivity: NAT Gateway & Internet Gateway

The two subnets reach the internet through different paths. The private subnet has no public IPs of its own — an Elastic IP is associated with the NAT Gateway, and that NAT Gateway gives the Monitoring Server and Ansible Controller outbound-only internet access. The public subnet, on the other hand, routes directly through an Internet Gateway — so the Web Server doesn't need its own Elastic IP at all.

This outbound path through the NAT Gateway's Elastic IP is exactly what powers Cloudflare Tunnel (cloudflared), running on the Monitoring Server: it opens an outbound-only connection to Cloudflare's edge via that Elastic IP. Cloudflare then maps monitor.nurinyazid.my to the tunnel — bringing Grafana live without any inbound rule or public IP on the monitoring server itself.

The Web Server, already reachable through the Internet Gateway, is exposed more simply: a Cloudflare DNS A record for web.nurinyazid.my points straight at its public IP. Separately, within the VPC, the Web Server's private IP (10.0.0.5) is scraped by Prometheus on the Monitoring Server via Node Exporter — this traffic stays entirely inside the VPC and never touches the internet.

04 Core Concepts

A quick primer on the three tools doing the heavy lifting in this stack.

Grafana

An open-source visualization and dashboarding tool. It doesn't collect data itself — it connects to data sources like Prometheus and turns that data into dashboards, graphs, and alerts.

  • Reads metrics from Prometheus
  • Builds real-time dashboards
  • Exposed at monitor.nurinyazid.my

Prometheus

An open-source monitoring and alerting system built for time-series data. It "scrapes" metrics from targets at set intervals via HTTP endpoints.

  • Pulls metrics from Node Exporter
  • Stores data in its own TSDB
  • Feeds Grafana for visualization

Ansible

An agentless configuration-management tool. Tasks are written as YAML playbooks and pushed to target hosts over SSH — no agent software required.

  • Installs the Grafana/Prometheus stack
  • Configures Node Exporter on hosts
  • Deploys the container on the web server

05 Building & Pushing an Image to ECR

The general workflow for getting a local Docker image into Amazon ECR, ready for the web server to pull.

01
Authenticate Docker to ECR
aws ecr get-login-password --region ap-southeast-1 \
  | docker login --username AWS --password-stdin \
  ecr_registery.dkr.ecr.ap-southeast-1.amazonaws.com
02
Build the image
docker build -t devops-bootcamp-final .
03
Tag it for ECR
docker tag devops-bootcamp-final:latest \
  ecr_registery.dkr.ecr.ap-southeast-1.amazonaws.com/devops-bootcamp-final:latest
04
Push to ECR
docker push ecr_registery.dkr.ecr.ap-southeast-1.amazonaws.com/devops-bootcamp-final:latest
05
Pull on the web server (via Ansible)
docker pull ecr_registery.dkr.ecr.ap-southeast-1.amazonaws.com/devops-bootcamp-final:latest

Handled inside playbook-ship.yaml — ideally using an IAM role attached to the EC2 instance rather than hardcoded credentials.
